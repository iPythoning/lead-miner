# ADR-0001：外贸获客线索引擎的信号源选型与产品落位

- 日期：2026-08-14
- 状态：已采纳
- 决策者：范大勇（产品与商业判断）+ Claude（方案与实现）

## 背景

急需获客。中国外贸出海的目标客户聚集在几个可识别的地方，最初设想是从
**招聘平台招外贸业务员的生产制造企业**、以及**中国制造网 / 阿里国际站的新注册会员**
入手，用大数据挖掘或渠道 API 找到精确联系方式（例如企查查匹配），抓取侧已有 wigolo。

同时提出两个更深的问题：

1. **ABM 视角**：我们的客户的客户也需要线索 —— 只不过他们的客户是**海外 B 端采购商**。
2. **产品视角**：能否把现有产品收口为「以获客为目的、直接给客户线索」？

约束：
- 合规（PIPL / GDPR / 平台 ToS / 刑事红线）
- 既有产品线切分不能破（`paibao.ai` FDE 高 touch vs `pulseagent.io` 自助 SaaS）
- 既有域名边界不能破（见各仓 AGENTS.md §6）

---

## 决策

### D1：ICP 优先级反转 —— 招聘平台放到最后，展会名录与广告投放者优先

| 信号源 | 意向 | 获取难度 | 法律风险 | **真实付费意愿** |
|---|---|---|---|---|
| 招聘平台招外贸业务员 | 高 | 高（反爬狠） | **高**（简历=刑事红线） | **中偏低** |
| 平台**现有付费会员** | 中高 | 低（供应商页公开） | 低 | **最高** |
| **展会参展商名录** | 高 | 低（公开） | 低 | 高 |
| 投英文广告的中国公司 | 最高 | 低（Meta 广告库有公开 API） | 无 | 最高 |

**选源的唯一标准：能证明这家公司「此刻正在为海外获客花钱或花力气」。**
静态企业名录（黄页、工商全量）不是信号，只是底库。

招聘平台看似意向最强，但**付费意愿反而低** —— 他们的解法是「招个人」，
要成交必须先说服对方换范式；且法律风险最高。故列为最后。

首个落地信号源选**广交会参展商名录**：意向高、完全公开、且参展本身证明「已经在为获客花钱」。

详细的七类信号源矩阵见 [`docs/sources.md`](../sources.md)。

### D2：海关提单数据作为共用底座 —— 「一鱼两吃」

```
一条中国出口提单 = [中国供应商] ←→ [海外采购商] + HS编码 + 数量 + 时间
                      ↑                    ↑
                   我们的线索池        卖给客户的交付物
```

同一份数据，**左边是我们要找的客户，右边是客户要找的买家**。这是把「我们获客」
与「客户获客」统一起来的底座，也是对背景问题 1（ABM / 客户的客户）的正面回答。

自带资格审查：能出现在提单里的公司，确定在做出口、有实单。

### D3：新建 `leads.paibao.ai`；**PulseAgent 维持 AI 数字员工定位不变**

对背景问题 2 的回答**不是**把 PulseAgent 收口成线索引擎，而是把它 6 个数字员工能力中的
「线索挖掘」单独抽出，落成 `paibao.ai` 产品线的子产品：

```
上游（9 类线索来源）           leads.paibao.ai        下游（继续变现）
独立站 · 社媒 · 广告投放    →                    →   AI 销售（跟进转化）
ABM · GEO · 冷邮件          →      【线索】      →   AI CRM（客户管理）
线下展会 · 陌生开发 · 转介绍 →                    →   …
                                    ↑
                            数据底座：海关提单（D2）
```

**为什么叫 leads 而不是 miner**：「线索」是客户视角的词，「挖掘」是实现视角的词。
更重要的是它**承上启下** —— 租户 onboarding 后立刻能拿到线索，获得感具体可感；
而**有了线索，才谈得上继续卖 AI 销售、AI CRM**。这是 land-and-expand：
先用线索让客户尝到甜头，再往下游扩。

因此 `leads.paibao.ai` 不是一个孤立工具页，而是**整个 paibao.ai 产品线的入口**，
其他能力挂在它后面。设计与排期都应服从这个定位。

**为什么落在 paibao.ai 而非 pulseagent.io**：

| | paibao.ai | pulseagent.io |
|---|---|---|
| 客户 | 中国 B2B 出海**大客户** | 全球外贸**中小企业** |
| GTM | **FDE 高 touch**（人工代运营、不暴露价格、单一 CTA） | 自助 SaaS（免费试用、自助注册、透明定价） |
| leads 归属 | ✅ | ❌ |

线索挖掘是重服务、需人工解读与代运营的能力，天然属 FDE 侧。入口经 `console.paibao.ai`。

### D4：合规红线（三条，不可越）

1. **企业公示联系方式可用**；个人手机号 / 邮箱 / 简历数据在 PIPL 下无合法性基础
2. **绝不碰招聘平台简历库** —— 抓公开职位是 ToS 违约级，抓简历是**刑事级**，差一个数量级
3. 交付**欧盟**买家线索必须带 opt-out（GDPR 正当利益路径的前提）

展会名录含负责人姓名与个人手机号的处理依据：展商在官方名录**主动登记的商务联系方式**，
属 PIPL「已合法公开的个人信息，在合理范围内处理」。实务三条：
**首次联络说明来源**（还能提高接通率）、**给退订方式**、**不转售**。

### D5：先手工验证转化率，再自动化放量

管道建好了才发现转化率是 0，等于白烧两周。**先手工打一批电话测出接通率与有效话术，
再决定自动化哪一段、放量到哪个品类。**

## 备选方案

| 方案 | 为何未选 |
|---|---|
| **从招聘平台起步**（最初设想） | 见 D1：法律风险最高、付费意愿反而最低。信号强 ≠ 好成交 |
| **把 PulseAgent 收口为线索引擎**（本 ADR 草案期的提法） | 会破坏既有产品线切分：PulseAgent 是自助 SaaS 低 touch，而线索挖掘是重服务 FDE 能力。**已废弃** |
| 把 leads 挂在 `pulseagent.io` | 同上，客户画像与 GTM 完全不同 |
| 给 `Lead.source` 枚举加「广交会」等值 | 要改 schema + 迁移 + 影响所有租户；届次信息用 tags 表达即可（trade-crm 只有 tags 可筛） |
| 在企微 SCRM 里重建一套 CRM | OpenSCRM 只有 customer/tag/群发/活码，无任何 CRM 核心概念；重建等于把 trade-crm 的 36 个模块再造一遍，且本仓是补丁制 fork。改为**只读代理**：线索只存 trade-crm 一份，企微侧是视图不是拷贝 |
| 先建完整管道再验证 | 见 D5 |

## 后果

**正面**
- 信号源选型有了统一标准（「此刻在为海外获客花钱」），新增源时按此判断，不再逐个争论
- 海关数据一次采购、两处变现，摊薄成本
- 产品序列清晰：leads 作入口 → AI 销售 → AI CRM，land-and-expand 有了抓手
- 合规边界前置，避免事后返工（简历数据一旦入库，清理成本极高）

**负面 / 代价**
- 放弃招聘平台意味着短期少一个高意向源
- 海关数据需采购，有现金支出，且尚未完成选型
- `leads.paibao.ai` 是全新产品化工作（当前只有采集端 CLI），排期不小

**后续需要注意**
- **D5 至今未执行**：广交会 139 届 26,269 行已全量入库，但**一通电话都还没打过**，
  转化率仍是 0 个样本 —— 这是当前最大的未验证假设，优先级高于继续导入更多名录
- 海关数据未采购，D2 的「一鱼两吃」尚停留在设计
- GEO 不必从零做：`content-factory` 的 `/research` 模块已有 SERP/GEO 能力，接入前先看它
- 新子域 `leads.paibao.ai` 走 `*.paibao.ai` 空间（47 共享 nginx），
  **绝不可踏进 `paibao.ai` apex**（apex + www 属 paibao-portal，`/app/*` 留给 PA 的支付/ICP 合规）；
  47 上签证书必须带 `--config-dir /storage/ssl/letsencrypt`
